# Database Design

## 1. Database responsibilities

MongoDB stores synthetic user records and supports the repository operations required by the authentication service. The application, not the client, owns query shape and authentication decisions.

Recommended database name:

```text
modern_database_attacks
```

Use a different database name for automated tests, such as `modern_database_attacks_test`.

## 2. Collections

### `users`

This is the secure collection. It must not contain plaintext passwords.

```json
{
  "_id": "ObjectId",
  "username": "alice",
  "passwordHash": "<bcrypt-or-argon2-hash>",
  "role": "student",
  "active": true,
  "createdAt": "ISODate",
  "updatedAt": "ISODate"
}
```

Rules:

- `username` is normalized once and stored consistently.
- `username` is unique.
- `passwordHash` is generated by the seed script or registration service.
- `active` is checked by the authentication service.
- Passwords and password candidates are never stored in logs.

### `lab_users`

This optional collection exists only to make the unsafe query behavior observable with a synthetic account. It must never contain a real credential.

```json
{
  "_id": "ObjectId",
  "username": "alice",
  "password": "synthetic-demo-password",
  "role": "student",
  "active": true
}
```

The collection must be clearly labeled as lab-only in code, README and the browser interface. It must not be used by the secure route.

## 3. Indexes

Create the following indexes during startup or through an explicit setup script:

```javascript
db.users.createIndex({ username: 1 }, { unique: true });
db.lab_users.createIndex({ username: 1 }, { unique: true });
```

The unique index prevents duplicate identities and makes the lookup behavior deterministic.

## 4. Repository operations

Allowed secure repository functions:

- `findUserByUsername(username)`
- `createUser({ username, passwordHash, role })`
- `setUserActive(username, active)`

The repository must not expose a generic `findOne(filterFromClient)` function.

The secure lookup has a fixed shape:

```javascript
users.findOne({
  username: normalizedUsername
});
```

The password is checked by bcrypt or Argon2 after the user document is returned.

## 5. Seed strategy

`scripts/seed.js` should:

1. Connect using the same configuration as the application.
2. Create required indexes.
3. Upsert one synthetic secure user.
4. Upsert one synthetic lab user if lab mode is explicitly requested.
5. Print usernames and non-sensitive setup information.
6. Never print or commit a real password or secret.

The seed operation should be idempotent so it can run repeatedly without creating duplicates.

## 6. Data validation

Application validation should enforce:

- Username is a string with a small length limit.
- Password is a string with a small length limit.
- Unknown request keys are rejected.
- Nested objects and arrays are rejected where scalars are expected.
- Usernames are normalized consistently.
- Database documents are validated before use.

Do not rely only on removing keys that begin with `$`. Explicit types and explicit query shapes are the primary defense.

## 7. Database failure behavior

If MongoDB is unavailable:

- Health should report a degraded or unavailable state.
- Login should return a generic service-unavailable response.
- The application must not expose a connection string or stack trace.
- Tests should verify that the process does not hang indefinitely.

## 8. Data lifecycle

- Test data is disposable.
- Lab data is synthetic and local.
- Production data is out of scope.
- `scripts/reset-db.js` may delete only the configured local test database.
- Any reset command must require an explicit environment check.
