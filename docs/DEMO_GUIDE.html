Kịch bản demo thao tác trực tiếp

Bạn tự nhập payload và gửi từng thao tác. Trang không chạy sẵn một loạt kịch bản. Form login gọi database thật của từng biến thể; tài khoản và yêu cầu là dữ liệu tổng hợp của CampusDesk.

1. Mở bốn bản demo

Biến thểDocker localVercel Production
SQL Unsafelocalhost:3001Mở SQL Unsafe
SQL Safelocalhost:3002Mở SQL Safe
MongoDB Unsafelocalhost:3003Mở MongoDB Unsafe
MongoDB Safelocalhost:3004Mở MongoDB Safe

Local cần Docker Compose đang chạy. Dùng `docker compose up -d --build --wait --wait-timeout 240` để khởi động; lệnh này giữ nguyên các volume hiện tại.

2. Chuẩn bị hai cửa sổ cho hai role

  1. Mở hai browser profile tách cookie, ví dụ Chrome thường và Edge/InPrivate. Hai cửa sổ cùng một profile sẽ dùng chung session.
  2. Cửa sổ User: đăng nhập student / Student@123.
  3. Cửa sổ Admin: đăng nhập admin / Admin@123. Có thể đăng xuất rồi dùng cửa sổ này để thử payload trên bản Unsafe.
  4. Tài khoản thứ ba để thử khóa/mở lại là student2 / Student2@123.

Tất cả tài khoản trên đều là dữ liệu demo. Không nhập mật khẩu hoặc thông tin cá nhân thật.

3. Tự bypass form SQL

  1. Mở SQL Unsafe, bấm Demo injection, nhập username admin, bật Nhập payload tùy chỉnh.
  2. Nhập vào ô SQL password payload rồi gửi:
' OR 1=1 #

Kết quả mong đợi: request POST /api/auth/login trả HTTP 200 và dashboard mở bằng role Admin. Trong Diagnostics, query được đánh dấu đã chạy. # là comment MySQL, làm phần kiểm tra mật khẩu phía sau bị bỏ qua.

Thử thêm các input khác bằng cách thay từng ô; mỗi lần chỉ gửi một request:

Username: admin' --␠
Password: not-the-password

Username: ' OR role = 'admin' --␠
Password: not-the-password

Username: admin
Password: ' OR '1'='1' --␠

Ký hiệu ␠ ở cuối chỉ nhắc rằng MySQL yêu cầu dấu cách sau --; khi nhập, nhấn Space một lần rồi gửi. Có thể xem thêm các payload định sẵn, nhưng hãy tự gõ vào ô tùy chỉnh để tường thuật từng bước.

4. Gửi cùng payload trên SQL Safe

  1. Mở SQL Safe, chọn cùng chế độ Demo injection.
  2. Nhập lại username admin và password payload ' OR 1=1 #.
  3. Kết quả mong đợi là HTTP 401, không tạo phiên Admin. Query tìm username có tham số; mật khẩu được kiểm tra riêng.
  4. Để đối chiếu hoạt động bình thường, nhập admin / Admin@123; đăng nhập phải thành công.

5. Tự bypass form MongoDB

  1. Mở MongoDB Unsafe, bấm Demo injection, nhập username admin, bật ô payload tùy chỉnh.
  2. Nhập JSON này vào ô Password object rồi gửi:
{"$gt":""}

Kết quả mong đợi: HTTP 200 và dashboard Admin. Đây là object truy vấn MongoDB, không phải mật khẩu dạng chuỗi: điều kiện $gt làm password predicate khớp dữ liệu tổng hợp.

Có thể tự thử thêm từng object JSON sau trên MongoDB Unsafe:

{"$gte":""}
{"$ne":"not-the-password"}
{"$regex":".*"}
{"$nin":["not-the-password"]}
{"$exists":true}

Ô tùy chỉnh nhận JSON object tự nhập, không giới hạn vào sáu preset. Giới hạn kỹ thuật của request là tối đa 16 KB JSON; input chuỗi unsafe tối đa 12.288 ký tự.

6. Gửi cùng object trên MongoDB Safe

  1. Mở MongoDB Safe, nhập username admin và cùng JSON {"$gt":""}.
  2. Kết quả mong đợi là HTTP 400; validation từ chối object trước truy vấn xác thực. Diagnostics ghi Chưa chạy cho truy vấn đăng nhập.
  3. Thử password sai dạng chuỗi để thấy HTTP 401, sau đó nhập Admin@123 để xác nhận đăng nhập hợp lệ vẫn hoạt động.

7. Xem request và phản hồi trong DevTools

  1. Nhấn F12, mở tab Network, bật Preserve log và lọc Fetch/XHR.
  2. Gửi payload từ form. Chọn POST /api/auth/login để xem Request Payload, HTTP status và Response.
  3. Sau khi vào dashboard, đối chiếu GET /api/auth/me, GET /api/dashboard, GET /api/tickets; Admin còn gọi GET /api/admin/users và GET /api/admin/audit.
  4. Diagnostics trong trang giải thích luồng ứng dụng; đó không phải trace SQL/MongoDB từ driver. Với payload tùy chỉnh, xem giá trị đã gửi trong Request Payload của DevTools.

Không chụp hoặc chia sẻ cookie, CSRF token hay header xác thực.

8. So sánh User và Admin; cho thấy tác động lên dữ liệu

  1. Trong cửa sổ User, mở Yêu cầu: user student chỉ thấy các yêu cầu do tài khoản đó sở hữu; không có trang Người dùng.
  2. Để chứng minh server cũng chặn API, mở Console trên cửa sổ User và chạy:
fetch('/api/admin/users').then(async r => console.log(r.status, await r.json()))
fetch('/api/tickets/ticket-001').then(async r => console.log(r.status, await r.json()))

Kết quả mong đợi: cả hai trả HTTP 403 cho user student; ticket-001 thuộc student2. Ticket-002 thuộc student và có thể mở bình thường.

  1. Trong cửa sổ Admin, mở Yêu cầu, chọn mã CD-1002, đổi trạng thái thành Đã xử lý và mức ưu tiên thành Cao, rồi lưu.
  2. Quay lại cửa sổ User và tải lại. Ticket-002 phải hiện thay đổi vừa lưu. Network cho thấy request PATCH /api/tickets/ticket-002 cập nhật bản ghi thật trong DB của biến thể.
  3. Trong Admin → Người dùng, khóa tài khoản student. Cửa sổ User mất quyền ở request kế tiếp; đây là tác động lên trạng thái tài khoản trong DB.
  4. Ở Admin → Người dùng, bấm Reset dữ liệu mẫu và xác nhận. Nút khôi phục 3 tài khoản seed và 12 yêu cầu seed để demo có thể chạy lại.
  5. Tải lại cửa sổ User. Tài khoản student được kích hoạt lại; CD-1002 trở về trạng thái và mức ưu tiên ban đầu.

9. Phạm vi dữ liệu và điều không nên kết luận

  • Form đăng nhập chính chạy trên database thật của biến thể và dùng tài khoản/yêu cầu tổng hợp. Sau khi vào được, bạn tự thao tác dashboard, role và chức năng CampusDesk.
  • Truy vấn đăng nhập SQL chính vẫn tắt multi-statement. Phần stacked statement và DROP TABLE nằm ở một connection riêng đến database lab campus_sql_unsafe_lab.
  • Thao tác xóa MongoDB chạy riêng trên database campus_mongo_unsafe_lab, collection lab_notes. Nó không xóa ticket hay account CampusDesk.
  • Phần tác động sau bypass được chứng minh qua chức năng Admin thật: sửa yêu cầu và khóa tài khoản. Không nói rằng payload đăng nhập đã xóa bảng.
  • Reset chỉ upsert các ID seed đã biết: admin-001, user-001, user-002, ticket-001 đến ticket-012. Nó giữ bản ghi tự tạo, session và audit; không phải nút khôi phục toàn bộ database.
  • Safe/unsafe dùng database tách riêng theo từng biến thể. Hãy chạy lại reset trên bản Admin tương ứng nếu bạn muốn khôi phục dữ liệu ở cả bốn bản.

10. Tự thao tác database sandbox live

Panel xuất hiện ở trang Nhật ký & demo của SQL Unsafe và MongoDB Unsafe khi connection sandbox được bật. Đăng nhập trước bằng tài khoản demo thông thường; thao tác trong panel không thay đổi phiên CampusDesk.

  1. SQL bypass trong sandbox: chọn Unsafe query, username labadmin, nhập password ' OR '1'='1' -- . Kết quả phải tìm thấy tài khoản lab. Chọn Safe query và gửi lại cùng input để thấy kết quả không khớp.
  2. SQL stacked statement: chọn Unsafe, giữ username labadmin, nhập password '; DROP TABLE lab_events; -- . Danh sách phía dưới báo bảng không còn. Dashboard CampusDesk vẫn chạy vì nó dùng database khác.
  3. MongoDB login: ở MongoDB Unsafe, chọn Unsafe và nhập object {"$ne":""} vào password. Kết quả sẽ khớp tài khoản lab; Safe từ chối kiểu object.
  4. MongoDB xóa dữ liệu: ở form xóa ghi chú, chọn Unsafe và nhập owner filter {"$ne":"alice"}. Hai tài liệu sẽ bị xóa, còn lại alice. Safe chỉ chấp nhận một tên owner dạng chuỗi.
  5. Sau khi quan sát kết quả, bấm Reset sandbox và xác nhận. Danh sách được tải lại từ database sau mỗi thao tác; reset khôi phục riêng dữ liệu lab.

Sandbox dùng user/database riêng, chỉ chứa dữ liệu tổng hợp. Local Docker tạo quyền lab riêng cho database lab. Vercel chỉ bật panel sau khi project unsafe được cấu hình URL sandbox riêng và user DB bị giới hạn vào database lab tương ứng. Link unsafe công khai cho phép người khác thay đổi hoặc reset chính sandbox đó.

11. Xử lý lỗi khi đang trình bày

Kết quảÝ nghĩa / thao tác tiếp
HTTP 400, SQL_SYNTAXPayload SQL làm câu truy vấn sai cú pháp. Thử payload đã ghi ở trên; với --, nhớ dấu cách cuối.
HTTP 400 trên Mongo SafeObject bị validation chặn trước truy vấn xác thực; đây là kết quả mong đợi.
HTTP 401Thông tin sai hoặc safe đã từ chối bypass. Kiểm tra username, rồi thử tài khoản demo đúng.
HTTP 403Phiên User bị chặn ở chức năng chỉ dành cho Admin hoặc ở bản ghi thuộc user khác.
HTTP 413 / JSON không hợp lệForm login chính vẫn dùng giới hạn request 16 KB; live lab cho phép body tối đa 4 MB. Kiểm tra JSON object hợp lệ và giới hạn request của nền tảng hosting.
Bảng SQL báo đã bị xóaĐây là kết quả mong đợi sau stacked payload. Dùng nút Reset sandbox, không dùng nút reset CampusDesk.
Panel live không xuất hiệnPanel chỉ hiện ở trang Nhật ký & demo của hai bản Unsafe khi URL và quyền truy cập database lab riêng đã được cấu hình. Xem Health/Logs của project tương ứng.
HTTP 503 / trang chưa kết nốiLocal: chạy docker compose ps, xem docker compose logs --tail 100 sql-unsafe hoặc tên service tương ứng, rồi thử lại. Vercel: mở trang Health/Logs của project để kiểm tra DB.
Reset báo lỗiĐăng nhập Admin của đúng biến thể, tải lại để lấy phiên/CSRF mới, sau đó thử reset lại.
