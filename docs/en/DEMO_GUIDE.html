Manual live demonstration

You enter each payload and submit each action yourself. The page does not run a batch of scenarios. The login form queries the real database for its variant; accounts and requests are synthetic CampusDesk data.

1. Open the four variants

VariantLocal DockerVercel Production
SQL Unsafelocalhost:3001Open SQL Unsafe
SQL Safelocalhost:3002Open SQL Safe
MongoDB Unsafelocalhost:3003Open MongoDB Unsafe
MongoDB Safelocalhost:3004Open MongoDB Safe

For local testing, start Docker Compose with docker compose up -d --build --wait --wait-timeout 240. This keeps existing Docker volumes.

2. Prepare two windows for the two roles

  1. Use separate browser profiles with separate cookies, such as Chrome and Edge/InPrivate. Two windows in the same profile share a session.
  2. User window: sign in as student / Student@123.
  3. Admin window: sign in as admin / Admin@123. You can sign out and use this window for the unsafe payload demonstration.
  4. The third account, for lock/unlock demonstration, is student2 / Student2@123.

These are demo accounts. Never enter real passwords or personal information.

3. Manually bypass the SQL form

  1. Open SQL Unsafe, choose Injection demo, enter username admin, and enable Enter a custom payload.
  2. Enter this in the SQL password payload field, then submit:
' OR 1=1 #

Expected: POST /api/auth/login returns HTTP 200 and opens the dashboard as Admin. Diagnostics marks the query as executed. MySQL treats # as a comment, removing the remaining password check.

Try these alternatives one request at a time:

Username: admin' --␠
Password: not-the-password

Username: ' OR role = 'admin' --␠
Password: not-the-password

Username: admin
Password: ' OR '1'='1' --␠

The visible ␠ marks a trailing space required after --. When typing it, press Space once at the end. You can inspect the presets, but type into the custom field to narrate each step yourself.

4. Submit the same payload to SQL Safe

  1. Open SQL Safe and choose Injection demo.
  2. Enter username admin and the same password payload ' OR 1=1 #.
  3. Expected: HTTP 401; no Admin session is created. The query uses a bound username and checks the password separately.
  4. For a normal login control, enter admin / Admin@123; it should succeed.

5. Manually bypass the MongoDB form

  1. Open MongoDB Unsafe, choose Injection demo, enter username admin, and enable the custom payload field.
  2. Enter this JSON in the Password object field and submit:
{"$gt":""}

Expected: HTTP 200 and the Admin dashboard. This is a MongoDB query object, not a string password; $gt changes the password predicate to match the synthetic data.

You can type these JSON objects one at a time on MongoDB Unsafe:

{"$gte":""}
{"$ne":"not-the-password"}
{"$regex":".*"}
{"$nin":["not-the-password"]}
{"$exists":true}

The custom field accepts JSON objects you enter; it is not limited to the six presets. The technical request limit is 16 KB of JSON; unsafe string inputs can be up to 12,288 characters.

6. Submit the same object to MongoDB Safe

  1. Open MongoDB Safe; enter username admin and the same JSON object {"$gt":""}.
  2. Expected: HTTP 400. Validation rejects the object before the authentication query. Diagnostics says the login query was not executed.
  3. Try a wrong string password to see HTTP 401, then enter Admin@123 to confirm a valid login still works.

7. Inspect requests and responses in DevTools

  1. Press F12, open Network, enable Preserve log, and filter to Fetch/XHR.
  2. Submit a payload. Select POST /api/auth/login to inspect Request Payload, HTTP status, and Response.
  3. After login, inspect GET /api/auth/me, GET /api/dashboard, and GET /api/tickets. Admin also calls GET /api/admin/users and GET /api/admin/audit.
  4. On-page diagnostics explain the application flow; they are not a SQL/MongoDB driver trace. For custom input, inspect the Request Payload in DevTools.

Do not capture or share cookies, CSRF tokens, or authentication headers.

8. Compare User and Admin; show database impact

  1. In the User window, open Requests. The student account sees requests it owns and has no Users page.
  2. To show that the server also enforces access, open Console in the User window and run:
fetch('/api/admin/users').then(async r => console.log(r.status, await r.json()))
fetch('/api/tickets/ticket-001').then(async r => console.log(r.status, await r.json()))

Expected: both return HTTP 403 for student; ticket-001 belongs to student2. Ticket-002 belongs to student and should open normally.

  1. In the Admin window, open Requests, select CD-1002, change its status to Resolved and priority to High, then save.
  2. Reload the User window. Ticket-002 should show the change. Network shows PATCH /api/tickets/ticket-002 updating the live database record for that variant.
  3. In Admin → Users, lock the student account. The User window loses access on its next request; this changes the account status in the database.
  4. In Admin → Users, click Reset demo records and confirm. The button restores the 3 seeded accounts and 12 seeded requests.
  5. Reload the User window. The student account is active again and CD-1002 has its original status and priority.

9. Data scope and claims to avoid

  • The main login form uses the real database for its variant and synthetic accounts/requests. After sign-in, you operate the CampusDesk dashboard, roles, and features yourself.
  • MySQL multi-statements remain disabled on the main SQL login connection. Stacked statements and DROP TABLE use a separate connection to campus_sql_unsafe_lab.
  • MongoDB delete actions use a separate campus_mongo_unsafe_lab database and lab_notes collection. They do not delete CampusDesk accounts or tickets.
  • Show post-bypass impact through real Admin functions: update a request and lock an account. Do not claim the login payload deleted a table.
  • Reset only upserts known seed IDs: admin-001, user-001, user-002, and ticket-001 through ticket-012. It preserves user-created records, sessions, and audit events; it does not restore the whole database.
  • Each safe/unsafe variant has its own database. If you want to restore all four, sign in as Admin on each variant and run its reset separately.

10. Operate the live database sandbox yourself

The panel appears on Audit log & demo in SQL Unsafe and MongoDB Unsafe when its isolated sandbox connection is enabled. First sign in with an ordinary demo account; panel actions do not change your CampusDesk session.

  1. SQL sandbox bypass: choose Unsafe query, use username labadmin, and enter password ' OR '1'='1' -- . The lab user should match. Select Safe query and submit the same input to see no match.
  2. SQL stacked statement: choose Unsafe, keep username labadmin, and enter password '; DROP TABLE lab_events; -- . The table list below reports that it is gone. The CampusDesk dashboard remains available because it uses another database.
  3. MongoDB login: on MongoDB Unsafe, choose Unsafe and enter the object {"$ne":""} as the password. It should match the lab account; Safe rejects the object type.
  4. MongoDB delete: in the delete-notes form, choose Unsafe and enter owner filter {"$ne":"alice"}. Two documents are deleted, leaving alice. Safe accepts only one plain owner string.
  5. After observing the result, click Reset sandbox and confirm. The page reloads its records from the database after each action; reset restores only the lab data.

The sandbox uses dedicated DB users and database names with synthetic data only. Local Docker grants the lab user access only to its lab database. Vercel shows the panel only after the unsafe project has a dedicated sandbox URL and database user scoped to that lab database. Anyone with a public unsafe link can change or reset that sandbox.

11. Troubleshooting during the presentation

ResultMeaning / next step
HTTP 400, SQL_SYNTAXThe SQL payload made the statement invalid. Try a payload above; for --, include the trailing space.
HTTP 400 on MongoDB SafeThe object was blocked by validation before authentication; this is expected.
HTTP 401Credentials are wrong or Safe blocked the bypass. Check the username, then try the documented demo account.
HTTP 403The User role was denied an Admin action or a request owned by someone else.
HTTP 413 / invalid JSONThe main login form still uses a 16 KB request limit; the live lab accepts bodies up to 4 MB. Check that the JSON is valid and that the hosting platform's request limit is not lower.
SQL table reports missingThis is expected after the stacked payload. Use Reset sandbox, not the CampusDesk data reset.
Live panel is not visibleThe panel appears only on Audit log & demo in the two Unsafe variants after each separate lab URL and database permission is configured. Check the project's Health/Logs view.
HTTP 503 / connection unavailableLocal: run docker compose ps and inspect docker compose logs --tail 100 sql-unsafe or the relevant service. Vercel: inspect the project's Health and Logs views for DB connectivity.
Reset failsSign in as Admin on the same variant, reload to get a fresh session/CSRF token, then retry.
