Prepare the hosted demo for Vercel

This branch contains deployment configuration. Preparing or building it does not publish a site. The existing main-branch deployments are separate.

$0 deployment setup

Use the following free plans for this personal, non-commercial teaching demo. No paid Vercel feature, subscription, purchased domain or database upgrade is required by the code. Plan selection and spending limits belong to the provider accounts; a source-code setting cannot change or verify their billing plans.

Project settings

Use the repository root, branch demo_updated, Framework Preset Other, and Node.js 22.x. Keep the build, install and output settings from vercel.json: npm ci, npm run build:vercel, and dist. There is no Docker or long-running server in Vercel.

Use a protected Preview deployment, targeted at demo_updated, for each Safe variant you need. Set VARIANT to sql-safe or mongo-safe. The hosted handler rejects production and both Unsafe variants. Use local Docker for the four-variant comparison.

Generate a session secret locally, then put its output into the appropriate project's environment:

node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"

Prepare database storage once

Use dedicated synthetic databases and database users. For SQL, create the selected database with UTF-8 support before running the command below. On the zero-spend TiDB Starter instance, create campus_sql_safe in its SQL editor; configure a different CAMPUS_DATABASE only if needed. Allow network access from the intended Vercel environment and the machine doing setup. A hostname inside Docker, such as mysql or mongodb, is not reachable from Vercel.

With that variant's environment variables set in your shell, run:

npm ci
npm run db:prepare:hosted

Run setup sequentially once per variant before serving requests. It creates tables or indexes and seeds three synthetic users and twelve tickets only if the user store is empty. It does not reset existing data. Do not use db:reset as a hosted setup command. Never run this against a database containing real application data.

The Vercel handler reuses a database connection pool per warm function instance. It does not create schema or reseed on requests. Sessions remain in the database across function instances. A SQL pool can use up to eight connections per instance; size the provider's connection budget for the number of instances you allow.

API routes are separate from the single-page frontend fallback; missing assets and documentation return 404. Historical screenshots and evidence are not included in the hosted static build. The other documentation pages describe the Docker lab and may link to localhost.

Hosted behavior and limits

Sessions use Secure, HttpOnly, SameSite=Strict cookies over HTTPS. The application trusts one hosting proxy for HTTPS detection and checks same-origin requests and CSRF tokens. Preview deployments need their own configured environment and isolated databases; do not seed or test against the existing main deployment's data.

Keep Preview authentication enabled to limit access to the synthetic class demo. The existing login throttle is per warm function instance; a shared limit requires a Vercel Firewall rule or a shared limiter before allowing traffic beyond a small demonstration. This deployment path is not a production security certification.

After you later choose to deploy, check /api/health, /api/config, normal login/logout, safe rejection, variant navigation and /docs/. A 503 during cold startup means configuration or database connectivity must be checked; connection details are not returned to the browser.
